# 「轻卡」每日饮食打卡 App —— 设计文档

- 日期：2026-08-20
- 状态：设计已评审（6 节设计逐节确认通过），待实现
- 项目仓库：`lightcal`

## 1. 概述

一款仅个人自用的 iOS 原生减脂打卡 App：每天通过拍照 / 语音 / 文字快速记录饮食，自动统计热量与蛋白质、脂肪、碳水摄入，对照目标计算缺口并给出补充食物建议；运动消耗自动读取 Apple Health（HealthKit）；根据历史摄入与消耗趋势动态估算减脂速率与目标达成预计时间。

### 核心目标

1. 录入摩擦最小化：拍照、语音、自然语言三种低摩擦入口
2. 数据可信：AI/识别结果必须经用户确认才落库；历史记录营养快照不随数据源变化
3. 动态洞察：减脂速率与达标时间由真实数据动态算出，而非用户设定
4. 隐私优先：数据仅存本机，照片不出设备 —— 作为产品差异化卖点

## 2. 关键决策（约束清单）

| 决策点 | 结论 |
|---|---|
| 产品形态 | iOS 原生 App（SwiftUI），仅 iPhone 个人自用 |
| 运动数据 | HealthKit 自动读取（含 Apple Watch 主动消耗） |
| 饮食录入 | 拍照识别 + 自然语言 + 语音输入 |
| 智能能力 | 本地 Vision 食物识别 + DeepSeek API 文本解析/营养估算（混合） |
| 数据存储 | 仅本地（SwiftData），无云同步 |
| 安装方式 | 免费 Apple ID 自签 + LiveContainer（免 7 天重签） |
| 目标设定 | 系统按身体数据计算 TDEE 与营养目标，可微调数值 |
| 减脂速率 | 派生值，由体重趋势与能量缺口趋势动态计算，非用户输入 |
| 饮水 | 每日饮水记录与目标（默认体重 × 30 ml） |
| 微营养素 | 暂不做；营养结构预留可扩展字段 |
| 媒体文件 | 照片/语音/模型响应即用即弃，不落盘、不建缓存目录 |

## 3. 数据模型

全部 SwiftData 本地存储。运动数据不建表（实时查询 HealthKit）；建议清单不建表（派生计算）。

### 3.1 UserProfile（用户档案，单条）

性别、出生日期、身高、初始体重、活动水平系数（久坐 1.2 / 轻度 1.375 / 中度 1.55 / 高强度 1.725）。

### 3.2 Goal（目标，保留历史版本）

- 存：目标体重、开始日期、开始体重、每日目标（热量/蛋白质/脂肪/碳水）、每日饮水目标
- 每日目标初值由系统按 TDEE 与安全默认缺口（500 kcal）生成，用户可微调具体数值；「系统默认值」与「用户微调后实际值」分开存储
- 每次修改生成新版本，旧版本留档，历史图表按时间对应各版本
- **减脂速率不落库**：由体重历史趋势与能量缺口趋势动态算出（见第 5 节），属派生值

### 3.3 FoodItem（食物模板：内置库 + 自定义）

- 名称、每 100g 营养、来源标记（builtin / custom）
- 内置库不建表：打包 JSON 随 App 发布，只读、秒查、零成本；覆盖高频常见食物（数百条级，含别名）；自定义食物入库，可改可删

### 3.4 FoodLogItem（打卡明细，核心表）

- 日期、餐次（早餐/午餐/晚餐/加餐）、食物名、份量(g)
- **营养快照**：热量/蛋白质/脂肪/碳水冗余存入本条记录 —— 数据源后续变化不影响历史记录真实性
- 来源标记（内置库/自定义/AI 估算）+ 录入时间

### 3.5 WaterLogItem（饮水记录）

日期 + 饮水量(ml)（+ 可选时间），一条一杯，快速累加。

### 3.6 WeightRecord（体重记录）

日期 + 体重。手动录入，可选写入 HealthKit；首次建档时从 HealthKit 读最近体重作初始值。

### 3.7 营养结构（可扩展）

营养快照存为 Codable 结构 `NutritionFacts`：固定核心字段（kcal / protein / fat / carb）+ `extras: [String: Double]` 扩展字典。当前只存核心四项；将来加维生素/矿物质只需加数据，无需 schema 迁移。

### 3.8 派生数据

每日汇总（摄入热量、三大营养素、消耗、缺口、饮水进度）均为查询时即时聚合，不落库。

## 4. 录入管线

三条入口，汇入同一条管线：

```
拍照 → Vision 本地识别 → 候选食物
语音 → 系统语音转文字 ──┐
文字 ──────────────────┴→ DeepSeek 解析成结构化条目
   → 营养补全（三层兜底）→ 可编辑确认卡片 → 用户点保存 → 落库
```

### 4.1 拍照路径

- iOS 内置 Vision `RecognizeFoodInSceneRequest`：免费、离线、照片不出设备
- 识别出 1~N 个候选食物类别（不含份量）：默认按中等份量填（一碗米饭 ≈ 200g），在确认卡片里改
- 识别失败或置信度低 → 降级为文字录入，不阻塞

### 4.2 语音/文字路径

- 语音用系统 `SFSpeechRecognizer`（设备端中文转写，免费），转完文字后与打字完全同路
- 文字送 DeepSeek，严格 JSON 输出约束返回 `[{食物名, 份量g, 餐次}]`
- DeepSeek 失败/超时/离线 → 本地正则兜底解析常见模式（`100g鸡胸肉`、`两个鸡蛋`）；再失败 → 原始文本原样保留进确认卡片让用户手动补全，**输入永不丢失**

### 4.3 营养补全（三层兜底）

1. 内置食物库精确匹配 → 本地算营养，零成本
2. 自定义食物匹配 → 本地算
3. 都没有 → DeepSeek 估算（每 100g 热量/蛋白/脂肪/碳水），打「AI 估算」标记，UI 用琥珀色直观区分

### 4.4 确认卡片（关键闸门）

- 拍照、语音、文字的所有结果都先进一张可编辑卡片：每行 = 食物 + 份量 + 营养，可增删改、可选餐次
- **任何 AI/识别结果不直接落库**，必须用户点「保存」才写入
- AI 估算条目可一键「存为我的食物」，之后精确匹配

### 4.5 失败处理原则

- 每条路径都有降级出口，任何情况下不丢用户输入
- 所有网络调用 10 秒超时 + 重试一次

### 4.6 媒体不落缓存（硬约束）

- **照片**：只在识别瞬间存在于内存，Vision 识别完立即释放；确认卡片只显示食物文字列表，不保存缩略图、不写临时文件
- **语音**：只做实时流式转写，音频数据不落盘、不保存录音；上传 DeepSeek 的仅是文字
- **AI 响应**：仅在确认卡片会话期内存在于内存，保存后仅营养快照随打卡记录落库；不建任何媒体缓存目录

持久化到磁盘的只有文字和数字（打卡明细、体重、目标、自定义食物）。

## 5. 目标与预测引擎

### 5.1 TDEE 计算（建立目标时）

- BMR 用 Mifflin-St Jeor 公式（按性别/身高/体重/年龄）
- TDEE = BMR × 活动系数
- 热量目标初值 = TDEE − 500 kcal（安全默认缺口），下限保护：**不低于 BMR**，防过度节食
- 蛋白质 = 1.6~2.0 g/kg 体重（默认 1.8，减脂保肌）；脂肪 ≈ 0.8 g/kg 或 TDEE 的 25%；碳水 = 剩余热量折算。全部可微调
- 饮水目标默认 = 体重 × 30 ml，可微调

### 5.2 每日收支（动态）

- 摄入 = 当日打卡热量合计
- 总消耗 = BMR + HealthKit 当日主动活动消耗
- 当日缺口 = 摄入 − 总消耗（负值 = 有热量缺口）
- 饮水量不参与热量收支与速率计算（水无热量），仅作独立健康目标展示

### 5.3 动态速率（两个派生指标）

- **体重趋势速率**：取最近 14 天内的体重记录做线性回归 → kg/周。体重数据点 < 3 个时不显示，提示「多记录几天」
- **能量趋势速率**：近 7 天平均缺口 ÷ 7700 kcal/kg × 7 → kg/周（1 kg 脂肪 ≈ 7700 kcal）
- 两个速率并排展示：「体重实际掉 X，按能量缺口理论上应掉 Y」—— 不一致时本身是有价值信号

### 5.4 达标时间预测（每次打开实时算，不落库）

- 剩余减重 = 当前体重 − 目标体重
- 预测速率 = 体重趋势速率 × 0.6 + 能量趋势速率 × 0.4（体重趋势权重大，反映真实结果）
- 预计天数 = 剩余减重 ÷ 预测速率，给**区间**而非单点：保守/按趋势/按目标缺口三种情景
- 体重数据不足时退化为纯能量速率预测；完全没数据时显示「先记录几天」
- UI 明示：趋势外推不是承诺，平台期/代谢适应会使速率衰减；达标后自动提示转入维持期热量

## 6. 建议补充食物清单

### 6.1 场景识别（针对当日实时缺口）

- 热量剩余额度 = 目标 − 已摄入；三大营养素各自缺口 = 目标 − 已摄入
- 分场景：蛋白不足 → 高蛋白食物；碳水不足且热量有余 → 主食类；脂肪已超但热量有余 → 低脂高蛋白；热量额度快用完且蛋白还差 → 只推荐蛋白质密度最高的食物（每 kcal 蛋白含量最大）

### 6.2 计算逻辑

- 候选池 = 内置食物库 + 用户自定义食物；**AI 估算条目不进候选池**
- 按营养素密度打分：蛋白场景 score = 蛋白(g)/热量(kcal)，碳水场景同理，取前几名
- 份量换算：缺口 ÷ 每 100g 含量 → 建议份量，取整到常见单位（个/碗/杯/g）
- 示例输出：「还差 28g 蛋白质 ≈ 100g 鸡胸肉 或 4 个鸡蛋 或 300ml 牛奶」

### 6.3 约束规则

- 推荐份量的热量 ≤ 当日剩余额度
- 每次给 2~3 个替换选项，排除当日已大量吃过的食物
- 建议条目旁给「一键添加」按钮，点一下进当日打卡（仍走确认卡片）

## 7. 界面结构与设计系统

### 7.1 信息架构

3 个主 Tab + 全局录入入口：

- **今日**（首页仪表盘）/ **趋势**（图表）/ **我的**（设置）
- 每个页面的浮动「+」按钮统一弹出：拍照 / 语音 / 打字三选一

### 7.2 今日页（仪表盘，自上而下）

1. 热量剩余额度大数字（目标 − 已摄入），下方蛋白质/脂肪/碳水三条进度条
2. 饮水卡：已饮/目标进度 + 快捷杯型按钮（250ml 杯 / 500ml 瓶 / 自定义）
3. 餐次时间线：早/午/晚/加餐分组列出食物条目，点开可改可删
4. 缺口建议卡：「蛋白还差 28g → 100g 鸡胸肉 或 4 个鸡蛋」+ 一键添加
5. 达标预测卡：实际速率 X kg/周、预计 Y 月 Z 日达标，点击展开保守/趋势/目标三情景区间

### 7.3 趋势页

- Swift Charts：体重折线（带趋势线）、每日摄入柱状 vs 目标线、每日消耗柱状、缺口折线
- 范围切换：周 / 月 / 3 月 / 全部
- 速率对比卡：体重趋势速率 vs 能量趋势速率

### 7.4 我的页

- 目标卡（目标体重、开始体重、达标预测）+ 修改目标（生成新版本留档）
- 自定义食物管理（增删改，含「从 AI 估算一键存为我的食物」入口）
- 身体档案：身高/体重/年龄/性别/活动水平
- 设置：DeepSeek API Key、HealthKit 权限、写回 HealthKit 开关、饮水目标、体重单位
- 数据备份：一键导出 JSON/CSV（纯本地存储，防数据丢失的最后保障）

### 7.5 全局交互

- 确认卡片为所有录入的统一闸门（半屏卡片，可编辑后保存）
- 无网络时打卡完全可用（内置库 + 自定义食物），仅 AI 功能降级，界面明示状态

### 7.6 设计系统（依据 ui-ux-pro-max 检索结果定制）

- **风格**：Soft UI Evolution（柔和层次 + 清晰对比），浅色为主、完整深色模式；App 名「轻卡」
- **配色**：主色 青 `#0891B2`、强调 健康绿 `#059669`、浅底 `#ECFEFF`、卡片白
  - 语义色：剩余热量 = 青、达标 = 绿、超支 = 红 `#DC2626`、AI 估算条目 = 琥珀标记
- **字体**：iOS 系统字体（SF Pro），数字用等宽数字对齐；全量支持 Dynamic Type
- **图表规范**：体重 = 折线 + 趋势虚线（数据点 < 4 时显示统计卡而非图表）；每日摄入 = 柱状 + 目标参考线，柱上常显数值标签；多系列用线型（实线/虚线）区分，不单靠颜色
- **动效**：200–300ms 轻动效 + 触觉反馈（保存打卡、快加饮水轻震）；尊重系统「减弱动态效果」
- **触控与状态**：最小触控目标 44pt、目标间距 8pt；AI 解析/识别期间显示 ProgressView，禁止空屏
- **图标**：SF Symbols 原生图标（不用 emoji 当图标）
- **隐私信号**：设置页和首次启动明示「数据仅存本机、照片不出设备」

## 8. 技术栈与工程结构

### 8.1 技术栈

- Swift 6 + SwiftUI，**部署目标 iOS 17+**（SwiftData、Swift Charts、NavigationStack、Vision 食物识别、触觉反馈全部原生可用；LiveContainer JIT-less 支持 iOS 16+，无冲突）
- 数据：SwiftData（纯本地）；健康：HealthKit；AI：Vision（本地识别）+ DeepSeek API（URLSession 直连，仅文本）；语音：SFSpeechRecognizer（设备端转写）；图表：Swift Charts
- **零第三方 UI 库**：SF Symbols + 原生动效，保持轻量和签名体积最小

### 8.2 工程结构（按职责分模块，隔离可测）

```
LightCal/
├─ App/                 入口、依赖装配
├─ Models/              SwiftData 模型 + 可扩展营养字典 Codable
├─ FoodDatabase/        内置食物库加载、匹配、营养查询
├─ Logging/             录入管线编排（三入口 → 解析 → 确认卡片数据）
│   ├─ PhotoRecognizer/   Vision 封装
│   ├─ SpeechTranscriber/ SFSpeechRecognizer 封装
│   └─ TextParser/        DeepSeek 客户端 + 本地正则兜底
├─ Nutrition/           营养补全三层兜底、份量换算
├─ HealthKitService/    HealthKit 读写封装
├─ Goals/               TDEE/BMR、动态速率、达标预测引擎（纯函数）
├─ Recommendations/     建议清单计算（纯函数）
├─ UI/                  页面与组件
└─ Resources/           内置食物库 JSON
```

设计原则：

- **计算层（Goals/Recommendations/Nutrition）是纯 Swift 函数**，不依赖 UI 与框架 → 直接单测
- **服务层（HealthKit/DeepSeek/语音/识别）全部走 protocol 抽象**，UI 只依赖协议 → 可注入 mock 测试
- 录入管线为「解析器链 → 统一中间结构 → 营养补全 → 卡片数据」的管线式组合，各环节可独立替换

## 9. 测试策略

- **单元测试**（重点）：TDEE/速率/预测公式与边界（数据不足、已达标、速率为零）；建议清单的换算/额度约束/排除规则；营养补全三层优先级；本地正则解析常见句式；营养字典序列化
- **集成测试**：SwiftData 落库查询（内存容器）；DeepSeek 响应 JSON 解码（用固定样例，不依赖真网络）
- **UI 冒烟测试**：打开 → 录入 → 确认卡片 → 保存 → 仪表盘更新
- **真机手工清单**：HealthKit 权限、拍照识别、语音转写、深色模式、LiveContainer 安装

## 10. 构建与安装

- 免费 Apple ID 签名 → Xcode 构建导出 IPA → 装入 LiveContainer（一次性配置）
- 设备目标 iOS 17+；iPhone 真机调试需经 Xcode

## 11. 明确不做（范围外，YAGNI）

- 维生素/矿物质全量跟踪（营养结构已留扩展口，将来按需加入）
- iCloud 同步、多设备
- App Store 上架
- 多人/社交/分享功能
- 照片存储、录音存储
- AI 直接写入历史（确认卡片闸门是硬约束）
